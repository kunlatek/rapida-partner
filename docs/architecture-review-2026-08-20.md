# Revisão de arquitetura — rapida-partner (2026-08-20)

Escopo desta rodada: tratamento de **tematização** (`IStyle`/`ITheme` em `src/interfaces/project-style.interface.ts`, campo `IProject.styles`). Não repete achados de `docs/architecture-review-2026-08-14.md` (nenhum dos achados anteriores tocava este arquivo).

## Resumo

Total de achados: **4** — 1 alta, 2 média, 1 baixa.

Por categoria: estrutura + consumo real (1), estrutura/nomenclatura (2), tipagem (1).

Evidência de uso real divergente/confirmada: **4** achados — todos confirmados com evidência real (nenhum teórico).

**Achados com risco de quebra "decisão manual" — não implementar sem revisão humana explícita:**
- **A** — destino da tematização como um todo (implementar de verdade, reduzir escopo da interface ao que é implementável, ou formalizar como recurso não suportado ainda) é uma decisão de produto, não uma correção mecânica.

## Achados

### [Estrutura/Consumo] `IStyle`/`ITheme` é uma DSL completa de tematização sem nenhum consumidor no gerador — tudo que é escrito hoje é decorativo
- **Severidade**: alta
- **Arquivo(s)**: `src/interfaces/project-style.interface.ts` (129 linhas: `IColorPalette`, `ITypography`, `IBorders`, `IShadows`, `IInputStyles`, `IButtonStyles`, `ILabelStyles`, `IFieldsetStyles`, `IComponentStyles`, `ITheme`, `IStyle`), `src/interfaces/project.interface.ts:54` (`styles?: IStyle[]`), schemas `src/schemas/project-style.ref.json` e `src/schemas/project-style-theme.ref.json`.
- **Achado**: a interface modela um sistema de tematização rico — paleta de cores (13 campos), tipografia, bordas, sombras, spacing, dimensões de layout, e estilos por componente (input/button/label/fieldset) — replicável por seção de layout (`overall`/`main`/`navBar`/`sideBar`/`footer`). Mas em todo `rapida-code-generator/src` não existe **nenhuma** referência a `project.styles`, `IStyle` ou `ITheme` fora de um único método órfão (ver achado B). O gerador nunca lê o campo `styles` do `IProject` em nenhum template, injector ou processor.
- **Evidência de uso real**: grep por `project\.styles` e por `IStyle\b`/`ITheme\b` em todo `rapida-code-generator/src` não retorna nenhuma ocorrência (confirmado). Do lado do dado, 2 dos ~20 projetos de `rapida-projects` investiram tempo real preenchendo o campo com detalhe: `rapida-projects/src/projects/backoffice/movie/movieBackoffice.ts:112-152` (tema completo em `main`: `headerHeight`, `typography`, `colors` com 7 campos, `shadows`, `borders`, `components.input` com 7 campos, `spacing`, `maxWidth`, `footerHeight`) e `rapida-projects/src/projects/aiAgent/katia/katia.ts:181-195` (tema em `main.colors`/`main.typography`). Um terceiro projeto, `rapida-projects/src/projects/backoffice/cartorio/cartorioBackoffice.ts:139-141`, deixa o campo vazio com o comentário `// futuramente: tema personalizado` — o próprio autor do projeto já sinaliza que sabe que o recurso não existe ainda. Nenhum desses três temas tem qualquer efeito visual no app gerado.
- **Impacto**: quem preenche `styles` (como em `movieBackoffice`/`katia`) está investindo esforço de design real — cores de marca, tipografia, espaçamento — que não chega ao produto final. É pior que um campo simplesmente não-lido: a interface é rica e convidativa o suficiente (autocomplete, tipos aninhados) para parecer uma funcionalidade pronta, quando é 100% aspiracional hoje.
- **Mudança sugerida**: decisão de produto antes de qualquer mudança de interface — (1) implementar a leitura de `project.styles` no gerador (gerar CSS custom properties/Tailwind config a partir do tema, ou no mínimo conectar o método órfão descrito no achado B), ou (2) se não é prioridade no curto prazo, reduzir a interface ao subconjunto que será implementado primeiro (ex.: só `overall.colors`, já que é o único subconjunto com algum código — ainda que morto — endereçando-o) e marcar o resto como roadmap fora do `IStyle` atual, ou (3) manter a interface como está mas documentar explicitamente (no próprio arquivo `.ts` e/ou README) que é um contrato não implementado, para não induzir autores de projeto a preenchê-la esperando efeito.
- **Risco de quebra**: breaking (decisão manual) — qualquer uma das três opções acima é uma decisão de escopo/produto, não uma correção mecânica de tipo.

### [Estrutura] Único ponto de leitura de tema no gerador (`ThemeService.applyCustomTheme`) nunca é chamado, e mesmo se fosse, lê só ~7 dos ~40 campos possíveis de `ITheme`
- **Severidade**: alta
- **Arquivo(s)**: `rapida-code-generator/src/frontend/angular/ui/flowbite/templates/base/services/theme.service.ts:32-52` (`applyCustomTheme`), comparar com `rapida-partner/src/interfaces/project-style.interface.ts:106-116` (`ITheme` completo).
- **Achado**: `ThemeService.applyCustomTheme(style: any)` é o único trecho em todo o ecossistema que sabe interpretar um objeto no formato `ITheme` — mas (a) o parâmetro é tipado como `any`, não como `IStyle`/`ITheme` importado de `rapida-partner`, perdendo qualquer garantia de tipo; (b) só lê `style.overall?.colors`, ignorando `main`/`navBar`/`sideBar`/`footer` — ou seja, ignora exatamente a parte que a documentação da própria interface (`project-style.interface.ts:118-121`, "allowing for different themes to be applied to different layout sections") promete como diferencial; (c) dentro de `colors`, só mapeia 7 de 13 campos (`primary`, `primaryContrast`, `secondary`, `secondaryContrast`, `background`, `error`, `success` — faltam `tertiary`, `tertiaryContrast`, `quaternary`, `quaternaryContrast`, `warning`, `info`); (d) ignora inteiramente `typography`, `borders`, `shadows`, `spacing`, `maxWidth`, `headerHeight`, `footerHeight` e todo o bloco `components` (input/button/label/fieldset) — exatamente os campos que `movieBackoffice.ts` preenche com mais detalhe; (e) **o método nunca é chamado** — grep por `applyCustomTheme` em todo `rapida-code-generator/src` retorna só a própria definição. `ThemeService` é injetado em `app-root.template.ts:19`, `dashboard-dynamic.template.ts:29` e `dashboard-static.template.ts:50`, mas nesses três arquivos só `isDarkMode`/`toggleTheme` são usados de fato (alternância manual claro/escuro via `localStorage`, mecanismo totalmente desconectado de `IStyle`).
- **Evidência de uso real**: grep confirma zero call sites de `applyCustomTheme` e zero leitura de `project.styles` em qualquer template que constrói `app-root`/`dashboard`. O par `themeName: "light"` escrito em `movieBackoffice.ts:114` e `katia.ts:183` sugere que o autor do projeto esperava que isso selecionasse entre temas claro/escuro — mas a alternância claro/escuro real do app gerado (`theme.service.ts:9-17`, `top-navbar.template.ts:194-200,396-397`) é um `signal` booleano independente, guardado em `localStorage`, sem nenhuma referência a `themeName`.
- **Impacto**: há dois mecanismos de "tema" coexistindo sem se falar — o mecanismo de verdade (dark/light via classe CSS `.dark`, funcional) e o mecanismo da DSL (`IStyle[]`/`themeName`, decorativo). O nome `themeName: "light"` no dado do projeto sugere fortemente que a intenção original era que os dois convergissem, e hoje não convergem.
- **Mudança sugerida**: se a decisão do achado A for "implementar", este é o ponto de partida concreto: (1) tipar `applyCustomTheme(style: IStyle)` importando de `rapida-partner`; (2) decidir como `overall`/`main`/`navBar`/`sideBar`/`footer` mapeiam para partes da UI gerada (aplicar `overall` como base e as demais como overrides por região, por exemplo); (3) cobrir os 13 campos de `IColorPalette` e os demais blocos (`typography`/`borders`/`shadows`/`components`) como CSS custom properties, não só os 7 hoje mapeados; (4) decidir explicitamente a relação entre `themeName` e o toggle claro/escuro existente (ex.: `styles` vira a fonte de verdade e o toggle escolhe entre duas entradas do array pelo `themeName`, substituindo a lógica atual de `localStorage`/`prefers-color-scheme` isolada).
- **Risco de quebra**: breaking (decisão manual) — envolve redesenhar a relação entre dois mecanismos de tema que hoje não se conhecem; não é um ajuste de tipo isolado.

### [Nomenclatura] `radius` (nível tema) vs `borderRadius` (nível componente) para o mesmo conceito dentro da própria `ITheme`
- **Severidade**: média
- **Arquivo(s)**: `src/interfaces/project-style.interface.ts:32-34` (`IBorders.radius`), comparar com `:46-54` (`IInputStyles.borderRadius`), `:59-70` (`IButtonStyles.borderRadius`), `:84-90` (`IFieldsetStyles.borderRadius`).
- **Achado**: dentro do mesmo arquivo, o mesmo conceito ("raio de borda") é nomeado `radius` no nível do tema (`ITheme.borders.radius`) e `borderRadius` no nível de cada componente (`input`/`button`/`fieldset`) — sem nenhum motivo estrutural para a diferença (não é um caso de `border.radius` vs. propriedade solta; ambos são propriedades de um objeto de estilo).
- **Evidência de uso real**: `movieBackoffice.ts:134-136` usa `borders: { radius: "4px" }` (nível tema) e, dentro do mesmo objeto de tema, `components.input: { ..., borderRadius: "4px", ... }` (nível componente, linha 142) — o mesmo autor, no mesmo arquivo, precisou escrever os dois nomes diferentes para o mesmo valor conceitual, confirmando que a inconsistência já se manifesta em uso real, não é só teórica.
- **Impacto**: baixo isoladamente (é sobre um campo hoje não consumido — ver achados A/B), mas relevante justamente para quando a implementação real acontecer: quem for implementar o mapeamento para CSS vai carregar essa inconsistência de nome adiante se não for corrigida antes.
- **Mudança sugerida**: unificar para `borderRadius` em todos os níveis (é o nome mais específico e já é maioria — 3 de 4 ocorrências), renomeando `IBorders.radius` → `IBorders.borderRadius`.
- **Risco de quebra**: breaking (migração mecânica) — rename simples de chave, único uso real localizado (`movieBackoffice.ts:135`), fácil de migrar por grep.

### [Tipagem] `themeName` é `string` livre e obrigatório, mas nada no ecossistema valida ou consome seu valor
- **Severidade**: baixa
- **Arquivo(s)**: `src/interfaces/project-style.interface.ts:123` (`IStyle.themeName: string`), `src/schemas/project-style.ref.json:16-18` (`"required": ["themeName"]`).
- **Achado**: `themeName` é o único campo obrigatório de `IStyle` (tanto no tipo TS quanto no JSON schema), o que sinaliza que ele deveria ser a chave de seleção entre múltiplos temas do array `styles[]`. Mas é tipado como `string` livre, sem união fechada (`"light" | "dark" | ...`) nem qualquer validação de unicidade dentro do array, e — como registrado no achado B — nenhum código lê esse valor para selecionar um tema.
- **Evidência de uso real**: os dois projetos que preenchem `styles` (`movieBackoffice.ts:114`, `katia.ts:183`) usam ambos `themeName: "light"` — nenhum projeto real declara um segundo tema no array (ex.: `"dark"`), então a função de "selecionar entre temas nomeados" nunca foi exercitada nem pelo lado do dado.
- **Impacto**: campo obrigatório sem uso real é atrito puro para quem preenche o objeto — obriga a escrever um valor que não influencia nada hoje.
- **Mudança sugerida**: se a decisão do achado A for "implementar", vale avaliar se `themeName` deveria ser uma união fechada (ex.: `"light" | "dark"`) alinhada ao toggle existente, em vez de string livre — mas essa decisão depende diretamente de como A/B forem resolvidos, então não deve ser tratada isoladamente.
- **Risco de quebra**: aditiva por enquanto (não requer nenhuma mudança até que A/B sejam decididos) — registrado aqui só para não perder o ponto quando a decisão maior for tomada.
